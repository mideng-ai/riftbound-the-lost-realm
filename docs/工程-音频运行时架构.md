> **状态：** READY_FOR_IMPLEMENTATION（ADR-TD-008 已拍板，等待音频总监合成参数规格）
> **引擎结论：** 裸 Web Audio API（见 `docs/流程-决策日志.md` ADR-TD-008，D-OPEN 已关闭）
> **依据：** 冻结契约 `src/domain/audio.ts`、`src/config/audioEventMapConfig.ts`；

## 1. 目标、边界与依赖方向

**目标：** 让「完全无声」的当前工程具备全套音效 + 4 BGM + 环境层的运行时播放能力，
全程零外部音频资产、首包零字节增量、移动端可解锁、可 headless 验证、可无泄漏销毁。

**边界（硬约束）：**

- `src/domain/`、`src/config/` 冻结契约**不改**；数值（优先级 40/30/20/10、`maxConcurrentVoices=16`、
  事件→音效映射）唯一来源是 `audioEventMapConfig.ts`，音频层只读不重定义。
- 不引入任何 `@babylonjs/core` 音频模块；Babylon 仅保留渲染职责。
- 配方数值唯一来源是音频总监规格；synth 是**纯解释器**，代码内不出现音色魔法数字。

**依赖方向（对齐 `docs/工程-技术架构.md` §2 分层约束）：**

```
main.ts ─▶ audio/ ─▶ domain/index.ts（音频契约 + 事件类型，仅 import type/函数）
                  ─▶ config/audioEventMapConfig.ts（只读数值与映射，经 domain 导出访问）
```

- `audio/` 处于 `main` 之下、`domain/config` 之上；`domain/`、`config/` **永不** import `audio/`
  （config 仍是纯数据叶子，满足 L2「config 不得 import domain/render/scenes/audio」）。
- `audio/` 可 `import type` domain 的 `AudioEventId` / `GameEventType` / `EventBusApi` / `RunPhase` / `BossPhase`，
  运行时仅调用 `resolveSfxForEvent` / `mixerPriorityOf` / `sfxForEvent` 等冻结函数。
- 依赖注入：`AudioRuntime` 构造接收 `bus: EventBusApi` 与可选的 `contextFactory` / `recipes` / `clock`，
  便于 headless 测试注入 mock（singleton 禁止）。

## 2. `src/audio/` 目录结构与职责

| 文件 | 职责 | 关键契约 / 约束 |
|---|---|---|
| `index.ts` | 桶导出：对外只暴露 `createAudioRuntime` 与必要类型 | 外部（`main.ts`）只 import 本文件，不深链内部模块 |
| `types.ts` | 全部类型：`SynthRecipe`（波形/ADSR/滤波/扫频/增益）、`Voice`、`BgmTrackId`、`AudioRuntimeOptions`、`ContextFactory`、`AudioClock` | 配方形状在此定义；纯类型，无运行时代码 |
| `recipes/sfxRecipes.ts` | `AudioEventId → SynthRecipe` 的配方表（下一轮由音频总监规格填入） | 键集合必须覆盖冻结契约的 `AudioEventId` 全集；编译期 `satisfies Record<AudioEventId, SynthRecipe>` 保证不漏。见 §6.1 口径核对 |
| `recipes/bgmRecipes.ts` | 4 曲目 + 环境层的分层配方（音序/和声动机/转调偏移） | 与 `docs/音频-背景音乐.md` §1 曲目结构一一对应 |
| `synth.ts` | 合成器：吃 `SynthRecipe` + 目标 `AudioContext`，构建 osc→filter→ADSR gain→输出节点图，返回可停止的句柄 | 纯解释器，无魔法数字；ADSR 用 `AudioParam` 自动化；噪声用自生成 buffer |
| `voicePool.ts` | 音源池：`play(recipe, priority)`，上限 `maxConcurrentVoices=16`；满池时按 `mixerPriority` 抢占最低优先级、同级抢占最老 | 优先级数值取自 `mixerPriorityOf(level)`；`onended` 自动回收；`dispose()` 停全部 voice |
| `bgmScheduler.ts` | BGM 调度器：4 曲目 + 环境层分层、lookahead 排程、Boss 三阶段转调 | 独立 `AudioContext.currentTime` 时钟；与 `boss.phase_changed` / `run.phaseChanged` 对齐；定时器可清理 |
| `contextUnlock.ts` | 解锁与生命周期：懒创建 `AudioContext`，首次用户手势 `resume()`，`visibilitychange` 挂起/恢复 | 返回 `AudioContext` + `dispose()`；监听器全部移除 |
| `AudioBridge.ts` | 事件桥：订阅 `EventBusApi` → `resolveSfxForEvent(type, payload)` → `voicePool.play`；部分 BGM 控制事件转发给 scheduler | 保存每个 `subscribe` 返回的 `Unsubscribe`，`dispose()` 逐个调用（**不**用 `clearAll()`，会误伤 UI 监听） |
| `AudioRuntime.ts` | 主类/组合根：组装上述模块，暴露 `start() / playSfx(id) / setMuted(b) / dispose()` | 生命周期总控；`dispose()` 逐层清理；`playSfx(id)` 供无事件映射的音效显式播放 |

目录形态：

```
src/audio/
├── index.ts
├── types.ts
├── AudioRuntime.ts
├── AudioBridge.ts
├── synth.ts
├── voicePool.ts
├── bgmScheduler.ts
├── contextUnlock.ts
└── recipes/
    ├── sfxRecipes.ts
    └── bgmRecipes.ts
```

**命名与规范**（对齐 `references/06-coding-standards.md`）：公开 API 带文档注释；
`strict` + `verbatimModuleSyntax`（类型用 `import type`）；毫秒用 `Ms` 后缀、`dt` 用秒；

## 3. 数据流

### 3.1 SFX 主链

```
GameEvent.publish(type, payload)              // 领域系统经共享 bus 广播
  → AudioBridge 订阅回调(type, payload)
  → resolveSfxForEvent(type, payload)         // 冻结契约：含 proc/pickup/boss.phase 动态解析
  → 对每个 AudioEventId:
        priority = mixerPriorityOf(档位)      // 档位由 AudioBridge 按事件类别归类，见 §3.2
        voicePool.play(recipe[sfxId], priority)
          ├─ 池未满 → synth(recipe, ctx) → 节点图 → masterGain → ctx.destination
          └─ 池已满 → 抢占最低优先级（同级最老）→ 停旧 voice → 放新 voice
        voice.onended → voicePool 回收
```

- 动态事件的「播什么」完全由冻结的 `resolveSfxForEvent` 决定：
  `proc.triggered`→元素、`resource.picked_up`→货币、`boss.phase_changed`→阶段，
  AudioBridge **不复制解析逻辑**。
- `AUDIO_EVENT_MAP` 中值为空数组（`run.phaseChanged` / `upgrade.offered` / `enemy.*` 等）的事件
  不产音效，但部分事件被 BGM/scheduler 消费（见 §3.3），桥接层需区分「无音效」与「需响应」。

### 3.2 混音优先级归类

`audioEventMapConfig.ts` 只给档位数值（bossWarn 40 / bossAttack 30 / affix 20 / normal 10），
不给「哪个 sfxId 属于哪档」的映射——该归类**由音频层数据驱动**放在 `recipes/sfxRecipes.ts`
（每条配方带 `priority: MixerPriorityLevel` 字段），不在代码里硬编码 if/else。
Boss 预警/攻击类走高档，词缀提示走 affix，其余 normal。
数值仍经 `mixerPriorityOf` 读取，档位变更不需改音频层代码。

### 3.3 BGM 与调度链（独立）

```
AudioClock（AudioContext.currentTime + lookahead 定时器）
  → bgmScheduler.tick()
      ├─ 按 run.phaseChanged(to) 选曲：
      │    metaHub → BGM-1 准备；running 0:00–7:30 → BGM-2 探索林；
      │    7:30–10:00 → BGM-3 高压战斗（预警点叠警报动机）；Boss → BGM-4
      ├─ 环境层：森林风声 / 裂隙低鸣，与任一曲目叠加、按区域/阶段混合
      ├─ boss.phase_changed(phase) → BGM-4 换层 + 转调（guardian→corruption→coreFrenzy）
      │    与 sfx_boss_phase_2 / _3 同事件对齐（同一 bus 事件，两条消费路径）
      └─ 交叉淡入淡出：gain 自动化在切曲/换层处 ramp，避免爆音
```

- `AudioBridge` 同时把 `boss.phase_changed` / `run.phaseChanged` 转发给 `bgmScheduler`；
  SFX 路径与 BGM 路径消费**同一条事件**，天然对齐 Boss 阶段切换音与音乐转调。
- 曲目时长分段（0:00–7:30 / 7:30–10:00 / 10:00+）来自 `docs/音频-背景音乐.md` §1，
  具体阈值注入配置，不写死在 scheduler。

## 4. 生命周期与防泄漏

| 资源 | 创建者 | 释放者 | 要点 |
|---|---|---|---|
| `AudioContext` | `contextUnlock`（懒创建） | `AudioRuntime.dispose()` → `ctx.close()` | 首次手势前不创建或创建后保持 suspended |
| 解锁/可见性 DOM 监听 | `contextUnlock` | `contextUnlock.dispose()` | `pointerdown`/`touchstart`/`keydown`/`visibilitychange` 全部 `removeEventListener` |
| EventBus 订阅 | `AudioBridge` | `AudioBridge.dispose()` | 逐个调用 `subscribe` 返回的 `Unsubscribe`；**不**调用 `bus.clearAll()`（会清掉 UI/combat 监听） |
| 活跃 voice / 节点 | `voicePool` + `synth` | `voicePool.dispose()` | 停全部 osc、断开节点；`onended` 也回收，防双释放需幂等 |
| BGM 定时器 | `bgmScheduler` | `bgmScheduler.dispose()` | `clearInterval`/`clearTimeout`；停 BGM voice |
| 静音 buffer（iOS 解锁用） | `contextUnlock` | 随 ctx 关闭释放 | 若规格需要 |

`AudioRuntime.dispose()` 顺序（组合根统一收口）：

```
1) AudioBridge.dispose()        // 先退订，杜绝 dispose 期间新事件触发播放
2) bgmScheduler.dispose()       // 清定时器 + 停 BGM voice
3) voicePool.dispose()          // 停全部 SFX voice
4) contextUnlock.dispose()      // 移除 DOM 监听
5) ctx.close()                  // 最后关闭上下文
```

- **`listenerCount` 归零断言**：dispose 后对订阅过的每个事件调用 `bus.listenerCount(type)` 应为 0
  （前提是这些事件无其他监听者；测试用独立 bus）。
- `AudioRuntime` 暴露 `start()` 幂等：重复调用不重复订阅/不重复建 ctx。

## 5. 与现有代码的接线点（精确文件 / 语义行号）

**共享总线的事实来源**：`Bridge.bus`（`src/scenes/CombatUiBridge.ts` L53–54 `readonly bus: EventBusApi = createEventBus()`）
是注入 `CombatRuntime` 与 UI 的同一条实例：

- `src/scenes/BootstrapScene.ts` **L294**：`const sharedBus = deps.ui?.bus ?? deps.uiBridge?.bus ?? undefined;`
- `src/combat/CombatRuntime.ts` **L87** `readonly bus: EventBusApi`、**L106** `this.bus = opts.bus ?? createEventBus();`
- `CombatUiBridge.sources.bus`（L68）与 `bridge.bus` 同一实例 → 传给 `createBootstrapScene({ ui: bridge.sources })`（main L73）。

**音频挂载点**：`src/main.ts` **L67–77** 的 `bridge` 创建与 `createBootstrapScene({...})` 调用附近。
建议紧随 L67 `const bridge = new CombatUiBridge();` 之后创建音频运行时并传入 `bridge.bus`：

```ts
// 语义示意（本轮不落代码，下一轮实现）
const mute = new URLSearchParams(location.search).get('mute') === '1'; // 与现有 ?debug=1 / ?perf=1 同风格
const audio = createAudioRuntime({ bus: bridge.bus, muted: mute });    // 共享 combat/ui 同一条 bus
// 用户首次交互解锁由 contextUnlock 内部绑定；无需在 main 手动 resume
```

- **为何用 `bridge.bus` 而非新建 bus**：只有共享实例才能收到 `combat.bus` 广播的
  `proc.triggered` / `boss.phase_changed` / `run.phaseChanged` / `resource.picked_up` 等全部离散事件。
- **`?mute=1`**：与现有 `?debug=1`（main L27）、`?perf=1`（L91）风格一致，供 QA/调试静音，不进玩法逻辑。
- **销毁**：`main.ts` 当前无 teardown；音频 `dispose()` 由后续页面卸载钩子或宿主 dispose 流程调用
  （下一轮实现时评估是否补一个最小卸载钩子，本蓝图不强改 main 结构）。
- **改动面**：`main.ts` 仅新增 import + 约 3–6 行接线（L67 附近），不改 `createBootstrapScene` 入参语义、
  不改 `CombatUiBridge` / `BootstrapScene` / `CombatRuntime` 的构造 signature。

## 6. 测试策略

沿用现有 `node:test` + `tsconfig.test.json` + `tests/prepare.cjs` 体系，新增 `test:audio`
脚本接入 `npm test` 链；参照 `08-templates` 的 verification-driven 原则「先测试后实现」。

### 6.1 可 headless 测（BLOCKING，注入 mock 依赖）

| 测试项 | 方法 | 断言 |
|---|---|---|
| 配方表结构完整性 | 编译期 `satisfies` + 运行期遍历 | 冻结契约 `AudioEventId` 全集全覆盖；每条配方字段合法（ADSR 时长≥0、增益有限、扫频端点>0） |
| 事件→音效接线 | mock `EventBusApi`，publish 各事件 | `resolveSfxForEvent` 产出的 sfxId 逐一进入 `voicePool.play`（含动态事件：proc/pickup/boss.phase） |
| 音效覆盖 | 遍历 `eventToSfx` 全部非空值 + 动态映射值 | 每个可达 sfxId 都能从配方表取到配方（不抛错） |
| 退订归零 | `AudioRuntime.dispose()` 后查 `listenerCount` | 每个订阅过的事件监听器数归 0；`Unsubscribe` 调用次数 = `subscribe` 次数 |
| 16 音源上限 | 连续 `play` 超过 16 个 voice（mock clock 不让 onended 触发） | 活跃 voice 恒 ≤ 16（`maxConcurrentVoices`） |
| 优先级抢占 | 池内填满 normal，再 play 一个 bossWarn(40) | 被抢占的是 normal 中最老的一个；bossWarn voice 在池内 |
| 静音开关 | `setMuted(true)` 后 publish 事件 | 不产生 voice（或 masterGain=0），断言可注入的 spy 计数 |
| BGM 选曲/转调 | mock `AudioClock` 推进到阶段边界 + publish `run.phaseChanged`/`boss.phase_changed` | scheduler 切换曲目、触发转调偏移；定时器在 dispose 后为 null |

mock 策略：注入 `ContextFactory` 返回假 `AudioContext`（节点为 spy 对象，记录 `connect`/`start`/`stop`/
`AudioParam` 自动化调用），无需真实音频设备、无随机、无真实计时依赖。

> **ID 口径核对（已上报主理人）**：任务书称「51 音效 ID」，但冻结 `src/domain/audio.ts` 的
> `AudioEventId` 联合实际展开为 **48 个**（42 个显式字面量 + `sfx_affix_${EliteAffixId}` 6 个模板实例）。
> 配方覆盖断言以**冻结契约的实际全集**为准；若音频总监规格确为 51，差额 3 个由主理人确认归属后再纳入，
> 本轮不改契约。

### 6.2 不测（ADVISORY / 交 QA，见 `06-coding-standards.md`「What NOT to Automate」）

- **真实听感**：音色是否符合规格、混音平衡、BGM 音乐性——不自动化。
- **平台解锁行为**：iOS Safari 首次手势 + 静音 buffer 解锁、Android Chrome 自动播放策略——真机验证。
- **真实延迟 / glitch / 采样率**：headless mock 无法覆盖，真机耳机试听并记录。
- **完整一局听感浸泡**：交人工 playtest，不写自动化。

**验证证据**：headless 测试结果进 `test:audio` 输出；真机听感结论由 QA 记录（玩家可听变更需实际运行留证，
不以「解析通过」代替验证）。
