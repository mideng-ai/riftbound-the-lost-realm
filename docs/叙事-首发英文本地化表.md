# 首发英文本地化表（NARRATIVE_EN_TEXT_TABLE V1.0）

> 交付：叙事总监 ｜ 状态：文案定案，接线待技术总监 ｜ 源文件：`src/text/en.ts`
> 命名唯一源：`docs/叙事-世界观与文案.md` §2 术语表；Boss / 事件文案同文档 §3 / §4。
> 本表只新增文件，未改动 `src/domain/`、`src/config/`、`src/ui/`、`tests/` 与叙事文档既有定案。

## 0. 这份表解决什么问题

`src/ui/uiText.ts` 的注释写得很直白：仓库此前**没有文本表实现**，UI 只定义 key 常量 + 注入式 resolver。宿主没注入 resolver 时，走的是 `debugTextResolver`，它调用 `keyLabel()` **从标识符反推可读标签**：

```
'ui.settle.victory'  →  去掉 ui. 前缀  →  'settle victory'  →  首字母大写  →  'Settle Victory'
```

这就是之前玩家看到 `Settle victory` 的原因——那不是文案，是调试标签。`identityTextResolver` 更诚实，直接返回 `ui.settle.victory` 原串，但同样不能上线。

`src/text/en.ts` 补上这个空缺：导出 `enTexts: Record<string, string>`，把每个 key 映射到真正的英文玩家可见文本。它是**纯数据叶子**，零 import、零逻辑，任何层都能引用；宿主只需把它包装成 `TextResolver` 注入即可。

**首发只有英语（en）。** 游戏表里没有任何中文，也没有中英对照、占位符或 `key`/`label`/`TODO` 残留。中文只出现在本说明文档里。

覆盖规模：**143 条**（`UI_TEXT_KEYS` 全部 **46** 个 key 一个不少 + **97** 条扩展条目）。

## 5. 给技术总监的接线提示

`src/text/en.ts` 零依赖，注入方式与现有 `TextResolver` 端口天然吻合：

```ts
// 宿主侧（例如 src/main.ts / EngineHost 的 UI 装配处）
import { enTexts } from './text/en.ts';
import type { TextResolver } from './ui/uiText.ts';

export const enResolver: TextResolver = (key) => enTexts[key] ?? key;
```

要点：

1. **未知 key 兜底必须存在**。`?? key` 保证动态拼 key（`enemy.<defId>.name`、`affix.<affix>.name`、`ui.scope.<scope>`、`event.<id>.name`）在漏配时退回原串，而不是 `undefined` / 空白。这些拼出来的 key 已全部覆盖，但兜底是安全网。
2. **不要用 `debugTextResolver` 上线**。它从标识符反推标签，正是 `Settle victory` 的来源。正式构建注入 `enResolver`；`debugTextResolver` / `identityTextResolver` 只留在 `?debug=1` 骨架验收路径。
3. **两条 key 路径指向同一文本**。`UI_TEXT_KEYS.bossPhase*` 与 `BOSS_PHASE_THEME.labelKey` 都是 `ui.boss.phase.*`；`UI_TEXT_KEYS.currency*` 与 `CURRENCY_LABEL_KEY` 同源。表里各覆盖一次即可，无需重复。
4. **文本冻结纪律**。首发后 `enTexts` 源字符串进入本地化冻结，改动需走设计变更流程；新增文案走"新增 key"，不改旧值。
5. **未挂载的 key 不要删**。`ui.settle.afterword`、`boss.attack.*`、`ui.warningShape.*` 等是为已规划演出预留的正式条目，删除会造成将来接线时重新走审阅。
