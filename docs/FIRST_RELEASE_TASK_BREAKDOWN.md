## 1. 任务分解原则

1. 所有任务均追溯到 FR-MH-01～FR-MH-15；没有来源需求的任务不得擅自加入首版。
2. 任务分为设计冻结、阶段2技术验证、阶段3 M1 原型、后续首版内容、发布验收。
3. **所有任务当前均为「未启动 / 规划中」**。阶段1文档工作不等于开发任务已经启动。
4. 设计依赖尚未获批时，相关实现任务保持阻塞；不得先写代码再补决策。
5. 不给出未经验证的人日、日历排期、性能承诺或发布日期。任务估算需在阶段1验收、阶段2技术 Spike 后重新进行。
6. 具体技术架构、模块边界和数据结构须在阶段2验证后确定；本任务树只描述交付结果。

## 6. 关键路径与风险控制

**当前规划关键路径：**
1. D-201 输入规则 → D-204 闪避输入兼容 → 移动/战斗原型。
2. D-202 撤离与死亡资产规则 → D-205 物品/背包规则 → D-206 营地资源循环 → 存档数据契约。
3. D-203 地图拓扑/撤离可达性 → M1 地图骨架 → 撤离/死亡闭环。
4. D-205 两种构筑定义 → 装备管理 → 构筑差异验收。
5. D-209 引导规格依赖稳定的输入、战斗、拾取、结算和营地流程。

| 风险 | 影响任务 | 控制方式 |

| 双端与性能目标没有设备证据 | T-009、T-011、T-032～T-034 | 真实设备矩阵测试后再设门槛 |

## 7. 任务完成定义（Definition of Done）

所有执行任务至少满足：
- 与已批准的需求/决策编号可追溯。
- 验收步骤可复现，记录实际结果而非只记录「已完成」。
- 无已知阻断性问题；未解决问题有严重度、影响与负责人接受记录。
- 涉及资源时具备来源与许可证记录。
- 不把未测试功能、占位内容或测试起点标成已验收。
- 相关文档、需求追踪矩阵与决策日志同步更新。
