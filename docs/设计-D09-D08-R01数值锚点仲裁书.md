## 裁定 1（D-09）：强化表 Lv5 = **32%**

### 1.1 为什么是 32%，而不是 20%

**决定性理由：证据链 3:1，且 20% 破坏了等差结构。**

支持 **32%** 的独立证据（三处，且全部是「正式表」而非「括号内顺手写的数」）：

| 来源 | 原文 | 性质 |
|---|---|---|
| `设计-设计总纲.md` §4.2 强化表 | Lv.2 +8% / Lv.3 +16% / Lv.4 +24% / **Lv.5 +32%** | 主表，逐级列明 |
| `总纲-项目规划书V1.md` §2.1 裁决 #1 | 「表中数值即该级总值」+「奇数级线性插值 **+4%/级**」 | 裁决条款 |
| `src/config/playerConfig.ts:81` | `weaponUpgradePctByLevel = [0, 0.08, 0.16, 0.24, 0.32]` | 已落地配置 |

支持 **20%** 的证据：**只有一处**——§2.1 算例括号内的「20%强化Lv5」。

**结构性反证（这条最硬）**：强化序列 `8, 16, 24, 32` 是严格公差 +8 的等差数列，而裁决 #1 说的「奇数级插值 +4%/级」正是公差的一半（8% ÷ 2 = 4%），两者互相印证。若 Lv5 = 20%，序列变成 `8, 16, 24, 20`，公差为 `+8, +8, −4`——不仅不等差，还出现**负增长**。一份写着「奇数级线性插值」的表不可能以负增长收尾。

**因此 20% 是笔误，不是设计意图。** 它极可能是把「32%」误抄成「20%」，但随后 A 区总和仍按 20+25 算成了 1.45，于是矛盾被冻结进文档。

### 1.2 算术还原

```
A = 1 + 32%（强化 Lv5） + 25%（熟练 Lv10 = 1.57）
单发 = 8 × 1.57 × 1.288 × 1.50 = 24.2659 ≈ 24.27/发
DPS  = 24.2659 ÷ 0.50 = 48.5318 ≈ 48.53
```

偏移量：`1.57 ÷ 1.45 − 1 = +8.28%`；`48.53 ÷ 44.8 − 1 = +8.33%`。QA 实测的「偏差 +1.87 单发」精确复现（24.266 − 22.411 = 1.855）。

### 1.3 Boss 2.9 分钟节奏承诺：**不受破坏，反而被修复**

这里必须拆开一件 QA 没拆的事：**§2.2 的「2.9 分钟」根本不是从 §2.1 的 44.8 推出来的。**

§2.2 原文：「DPS 峰 35–50，走位有效系数 0.7 → 有效 30–40；6000 ÷ 35 ≈ 171s ≈ 2.9 分钟」。

它除的是 **35**——§2.3 阶段表的 DPS 带**下沿**，不是 §2.1 的 44.8。两份基准本来就不同源：§2.1 是「装备满配单发校验」，§2.2 是「Boss 战节奏校验」。**锚点从 44.8 平移到 48.53，§2.2 的 171s 一秒都不变。** 用「Boss 2.9 分钟」否决方案 A 是不成立的。

反过来说，方案 A 实际上**修掉了一个旧锚点下的隐性破线**：

| 口径 | 旧锚点 44.8 | 新锚点 48.53 | 2–3 分钟带 |
|---|---:|---:|---|
| 无衰减 | 133.9s = **2.23 分** | 123.6s = **2.06 分** | 两者 ✅ |
| ×0.8（与「有效 30–40」自洽） | 167.4s = **2.79 分** | 154.5s = **2.58 分** | 两者 ✅ |
| ×0.7（原文声称） | 191.3s = **3.19 分** | 176.6s = **2.94 分** | 旧锚点 ✗ **破 3 分**；新锚点 ✅ **守住** |

**在 §2.2 自己声称的 0.7 口径下，旧锚点会让 Boss 战拖到 3.19 分钟，直接违背 2–3 分钟红线；新锚点刚好守在上沿 2.94 分。** 换句话说：若为了保 44.8 而选方案 B，你保住的恰恰是一个会让 Boss 战超时的锚点。

> 附带记录：§2.2 的「35–50 × 0.7 → 有效 30–40」本身就是第二个算术错误（35×0.7 = 24.5，不是 30）。这单列为 **Q-NEW-2**（见 §6），不并入 D-09 裁定，但它必须修，因为「有效 30–40」直接支撑了 171s 这个数。

|---|---|---|
| Boss 6000 HP ≈ 2.9 分钟 | ✅ 守住 | ×0.7 口径 2.94 分、×0.8 口径 2.58 分，全在 2–3 分带 |

### 1.5 必须如实上报：锚点平移 **不能** 修复 TTK 红线（这不是 D-09 能解决的）

这是我要主动挑明的一点：QA 问「锚点变了会不会破坏 TTK 红线」——答案是**红线本来就已经破了，与选 A 还是选 B 无关**。

以新锚点 24.27 单发、四阶段 HP 缩放（×1.0 / ×1.3 / ×1.8 / ×2.4）计算：

| 阶段 | 猎犬 HP / TTK | 投射者 HP / TTK | 影跃者 HP / TTK | 滋养体 HP / TTK |
|---|---|---|---|---|
| 1 热身 ×1.0 | 20 / 0.82s | 15 / 0.62s | 25 / 1.03s | 40 / 1.65s |
| 2 展开 ×1.3 | 26 / 1.07s | 20 / 0.80s | 32 / 1.34s | 52 / 2.14s |
| 3 升压 ×1.8 | 36 / 1.48s | 27 / 1.11s | 45 / 1.85s | 72 / 2.97s |
| 4 高压 ×2.4 | 48 / 1.98s | 36 / 1.48s | 60 / 2.47s | 96 / 3.96s |

（旧锚点 22.4 下 S1 为 0.89 / 0.67 / 1.12 / 1.79s——更差。）

**红线「普通怪 TTK 1.5–2.5s」在阶段 1–2 全线不成立，阶段 3–4 才勉强进入。** 而且不是「慢」而是「太快」：单发 24 对 HP 15–40 的怪意味着 1–2 发秒杀，这会让「打击感」和「怪物潮压迫」同时塌掉。

同样的检查也适用于另外两条红线：

- **玩家 8–12 次受击死亡**：猎犬 8 伤 → 12.5 次 ✅；影跃者 10 伤 → 10 次 ✅；精英 12 伤 → 8.3 次 ✅；**但投射者 6 伤 → 16.7 次 ✗，滋养体 5 伤 → 20 次 ✗，Boss 单次 18–30 → 3.3–5.6 次 ✗**。
- **Boss TTK 2–3 分钟**：✅ 见 §1.3。

**裁决立场**：D-09 只裁定「锚点数值谁对」，不裁定「TTK 红线怎么救」。TTK 红线破口单独立项 **Q-NEW-3**（见 §6），由我在下一轮系统设计中提出怪物 HP 曲线与武器基础伤害的联合重标定方案，**不得**用「把强化改回 20%」这种方式掩盖。

## 裁定 2（D-08）：熟练 Lv10 = **25%**，实现路径为「每级 +2% + Lv10 里程碑 +5%」

### 2.1 为什么不能选「每级 2.5%」

两种读法在数学上都能得出 25%，但代价完全不同：

| 读法 | Lv10 结果 | 需要改动的文档 | 代价 |
|---|---|---|---|
| ① 每级 2.5% | 25% ✅ | **改写** `设计-设计总纲.md` §6.4「+2%」→「+2.5%」 | 改了主表语义，且与 §6.4 的魔法剑熟练、森林生存「+2% / +1%」的整数节奏不齐 |
| **② 每级 2% + Lv10 里程碑 +5%** | 25% ✅ | **不改** §6.4 原文，只**新增**一条里程碑规则 | 需要一条新规则，但不动已确认文本 |

**我选 ②。** 理由：

1. **「不动已确认文本」优先于「少写一条规则」**。§6.4 的状态是「规则已通过」，改它要走正式变更；而「Lv10 里程碑」是一条**新增**，不改任何既有数值语义。
2. **② 保留了三方向的一致节奏**（熟练 +2%/级、生存 +1%/级，都是整数步进），只把「满级」做成一个显式节点。这是 roguelite 里非常成熟的写法：满级前是平滑线性，满级给一次性跨越，让玩家在 Lv9→Lv10 有明确的「冲顶」动机。
3. **② 的数值梯度更健康**。方案①每级恒定 +2.5%，Lv9→Lv10 只值 +2.5%；方案②在 Lv9→Lv10 给 +7%（18%→25%），这是**该局外成长线的最后一个决策点**，值得有一次明显的收益跃升。

### 2.2 完整 Lv0–Lv10 熟练值表（裁定采用方案②）

`metaGrowth.masteryPctPerLevel = 0.02`，**新增** `masteryMilestoneBonus = { level: 10, pct: 0.05 }`。

| Lv | 熟练加成 | A 区（+32% 强化） | 单发（B=1.288, C=1.50） | DPS |
|---:|---:|---:|---:|---:|
| 0 | 0.0% | 1.32 | 20.40 | 40.81 |
| 1 | 2.0% | 1.34 | 20.71 | 41.43 |
| 2 | 4.0% | 1.36 | 21.02 | 42.05 |
| 3 | 6.0% | 1.38 | 21.33 | 42.67 |
| 4 | 8.0% | 1.40 | 21.64 | 43.29 |
| 5 | 10.0% | 1.42 | 21.95 | 43.91 |
| 6 | 12.0% | 1.44 | 22.26 | 44.53 |
| 7 | 14.0% | 1.46 | 22.57 | 45.15 |
| 8 | 16.0% | 1.48 | 22.87 | 45.75 |
| 9 | 18.0% | 1.50 | 23.18 | 46.37 |
| **10** | **25.0%**（18% + 5% 里程碑） | **1.57** | **24.27** | **48.53** |

> 魔法剑熟练、森林生存同构：剑熟练 Lv10 同样 +25%（每级 2% + 里程碑 5%）；森林生存每级 +1%，Lv10 里程碑 **+5% 上限生命**（100 → 145）。森林生存的里程碑也须同步登记，否则三方向节奏不一致。

### 2.3 成本曲线复核（顺带发现，不影响裁定）

`C(L) = 100 + 50 × (L − 1)`，Lv0→10 总成本 = **3250 金币**。按 §6.2 掉落（普通怪 1、元素怪 2、精英 8–12、Boss 80–120）粗估每局 150–250 金币，满级需 **13–22 局**。这个量级对 10–15 分钟一局的 roguelite 属于偏长但不异常，登记为 **Q-NEW-1** 交由经济校准，不在本次裁定范围。

## 裁定 3（R-01）：C 区总上限 **选 ① 保留 + 如实标注不可达**，并**明确否决 ②**

### 3.1 为什么必须是 ①，不能是 ②

QA 列出的三个选项里，**②是唯一会造成实际数值灾难的**，而它看起来最「工整」（0.5 + 1.0 = 1.5 恰好触边）。必须说清楚：

**若把 `armorBreak` 加进 `C_ZONE_DERIVED_CATEGORIES`，破甲会被双计。**

现有实现（`src/domain/damage.ts`）中，破甲走的是**目标维度独立乘区**：

```ts
const armorBonus = armorBreakApplicable ? clampFinite(...) : 0;
const outgoing = raw * (1 + armorBonus);   // 乘在 A×B×C 之后
```

若再把 armorBreak 计入 C 区总量，则 Boss 战实际计算变成：

```
C   = 1 + min(damage 1.0 + armorBreak 0.5, 总上限 1.5) = 2.50
最终 = 8 × A × B × C × (1 + armorBreakBonus)
     = 8 × 1.57 × 1.288 × 2.50 × 1.50 = 121.3 DPS
Boss 战 = 6000 ÷ (121.3 × 0.7) ≈ 71 秒
```

**Boss 战从 2.94 分钟塌到 1.18 分钟，直接击穿 2–3 分钟红线。** 而且它不是「有意为之的 1.5 边界」，是一个纯粹的重复计价 bug。所以「0.5 + 1.0 = 1.5 恰好触边」不是设计巧合，而是**危险信号**：它说明 1.5 这个数字当初可能是拿「破甲 0.5 + 伤害 1.0」凑出来的，而这个凑法本身就错了。

### 3.2 为什么不选 ③（删掉总上限）

③ 在当前卡池下与 ① **完全等价**（C 上限都是 2.00），但它是**净损失**：一旦未来新增「全属性增伤」「对 Boss 增伤」「事件临时增伤」这类**不属于 damage 但直接放大单发**的类别，没有总上限就意味着它们可以叠加到任意量级。这类卡池扩展在 roguelite 里几乎必然发生（现在 15 张卡，M1 后必然要加）。

### 3.3 这个上限在玩法上想防什么（回答你的问题）

**它防的是「跨类别复合放大」——即多套互不相关的 C 区增益同时点满后的乘积爆炸。**

具体地，它防这四种情形：

1. **卡池扩张后的隐性叠加**：新增一类「法术强度 +x%」后，它与 damage 类各自 +100%，C 变成 3.00，A×B×C 直接从 1.57×1.288×2.00 = 4.04 涨到 6.06（+50%）。总上限在这里是**唯一**的拦截点。
2. **事件 buff 的无限叠加**：§2.1 算例里的「古老祭坛 20%」属于局内事件 buff。若未来事件设计成可重复触发（宝箱连开），没有总上限就是线性通胀。
3. **UI 无法向玩家解释的数值**：面板显示「局内伤害加成 +180%」但实际只吃 +100%，如果没有总上限约束，玩家看到的数字会失控并破坏「数值可读性」这条设计原则。
4. **平衡团队失去单一刹车点**：总上限是一个**一改就能全盘收敛**的旋钮（Tuning Knob）；分散在各类别里则是 8 个旋钮，每次调平衡要同时动 8 处。

### 3.4 但必须附一条阻塞级修正：**当前 C 区数值带本身与断言不符（Q-NEW-4）**

按 `damageConfig.caps.inRunDamagePct = 1.0`，**C 区在现卡池下的实际最大值是 2.00**（damage 满配）。而 §2.3 的 Boss 期 DPS 带是 35–50，在新锚点 A=1.57 / B=1.288 下：

| C 值 | DPS | 与 35–50 带 |
|---|---:|---|
| 1.50 | 48.5 | ✅ 带内偏上 |
| 1.60 | 51.8 | ✗ 超上沿 |
| 1.75 | 56.6 | ✗ 超 13% |
| **2.00（damage 满配）** | **64.7** | ✗ **超上沿 29%** |

**也就是说：只要玩家把 damage 类点满（这在 roguelite 里是必然发生的），Boss 期 DPS 就会冲上 64.7，超出 §2.3 的 35–50 带上沿 29%，Boss 战被压到 2.21 分钟以下（×0.7 口径 1.55 分钟）。**

这不是 R-01 的直接结论，但它决定了 R-01 该写成什么值。所以我的裁定是：**保留总上限机制的同时，把它的数值从 +150% 下调到 +60%（C = 1.60）**，理由是反向解算：A=1.57 / B=1.288 下要压住 DPS ≤ 50，需 C ≤ 1.60。

> 但注意：这样 C 区总上限（+60%）会**低于** damage 单类上限（+100%），使单类上限变成死代码，两者顺序反转。**这是一个结构性冲突，不能在本裁定里单方面拍板**——它牵涉到「damage 单类上限 +100% 是否也该下调」。因此我把它登记为 **Q-NEW-4（阻塞 R-01 定稿）**，并给出我的推荐解法（见 §6）。
