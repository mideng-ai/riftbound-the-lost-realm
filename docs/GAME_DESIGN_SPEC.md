## 3. 单局核心循环

### 3.1 本轮已明确的体验方向

状态：**体验方向已由负责人明确选择；不等于具体玩法规则已确定。**

- **整体节奏：探索与紧张并重。** 前段应给玩家观察环境、熟悉局势和探索搜刮的空间；随着玩家主动深入、接近高价值目标或选择高风险遭遇，紧张感逐步上升。
- **四大体验均衡：** 魔法战斗、探索搜刮、撤离风险决策、装备成长均应在一局中有存在感，不把整局做成单纯刷怪、单纯开箱或单纯逃生。
- 四大支柱是设计权重与体验目标，不要求每一分钟平均分配，也不应为追求形式上的平均而牺牲节奏。

### 3.2 单局时长口径提案

状态：**提案/待确认。**

- 建议将 10–15 分钟定义为「从进入地图开始，到撤离/死亡结算为止」的战局时长。
- 营地整备放在战局外，不计入这 10–15 分钟；进入地图前的选装与整理应保持轻量，避免准备阶段拖慢核心循环。
- 以上是计时口径建议，尚未成为 D-006 的新增细则；若负责人希望将营地整备也计入单局时长，需要再调整节奏预算。

### 3.3 建议的战局节奏分段

状态：**提案/暂定节奏预算，不是硬性计时脚本。** 玩家可以在适当时机提前撤离；各阶段的遭遇数量、掉落数量和具体事件均待后续设计与测试。

| 战局时间 | 阶段 | 体验目标与建议内容 |
|---|---|---|
| 0:00–1:30 | 进入与观察 | 让玩家快速读懂周围环境、主要方向和初步威胁；给出低压力的移动、观察与首次探索机会。 |
| 1:30–4:00 | 初次探索与战斗 | 安排早期普通敌人或轻量遭遇，让玩家使用基础战斗能力；附近应存在可发现的资源或奖励，让战斗与探索互相推动。 |
| 4:00–7:00 | 探索分支与奖励 | 鼓励玩家在相对安全的推进路线和更有吸引力的支线目标之间作选择；通过宝箱、资源点或事件形成搜刮期待。 |
| 7:00–10:00 | 风险上升与强遭遇 | 让深入区域的威胁更明显，可安排精英敌人或更复杂的战斗情境；更高价值的机会应伴随可理解的风险。 |
| 10:00–12:00 | 价值评估与撤离抉择 | 玩家结合已获得的战利品、当前生存状态和继续探索的预期收益，判断是否结束本局。此时应让撤离成为有意义的主动选择。 |
| 12:00–15:00 | 可选的高风险目标与收尾 | 仍愿冒险的玩家可以挑战更深区域或高价值目标，再寻找机会结束本局；不应强迫每局都挑战 Boss 或走完整个时间段。 |

节奏说明：

1. 上表是目标体验的时间参考，不要求每局严格按分钟触发事件。
2. 不应把 Boss 设为每局必打的强制终点；Boss 出现频率、触发方式和是否属于可选目标仍待设计。
3. 撤离不应被设计成只能在最后几分钟考虑的按钮。建议玩家在战局中逐步形成「现在已获得什么、继续冒险还可能得到什么、当前风险是否值得」的判断；撤离点的开放时机和具体操作仍待 D-202、D-203 讨论。
4. 若玩家在较早阶段已经获得满意收获，允许其选择较短战局；若玩家主动承担更高风险，则可将战局延伸至 12–15 分钟区间。
5. 不建议仅靠全局倒计时强制制造紧张感。更优先考虑用区域危险程度、遭遇强度、路线选择和玩家当前状态逐步构成压力；是否加入时间压力机制尚未决定。

### 3.4 完整循环节点

状态：**流程框架提案；具体系统规则待确认。**

1. **营地整备（战局外）：** 玩家查看已有装备与资源，选择本局准备使用的配置。整备内容和操作深度受 D-205、D-206 影响，暂不规定槽位、升级或消耗规则。
2. **进入裂隙：** 玩家进入本局地图，快速识别周围环境、可探索方向和当前威胁。
3. **探索与选择路线：** 玩家寻找资源、宝箱、事件或通往高风险区域的路线；探索应提供选择，而不是只沿唯一通道前进。地图的实际生成方式与布局由 D-203 决定。
4. **遭遇与魔法战斗：** 玩家根据敌人行为选择攻击、技能和走位方式。战斗应有明确的威胁提示、命中反馈和战后喘息空间；具体操作、技能和防御机制分别由 D-201、D-204 讨论。
5. **搜刮与构筑价值：** 玩家获得装备或资源，并逐步增加本局收获及跨局成长可能性。搜刮物品如何影响即时构筑、装备槽位、词条和资源用途，均由 D-205、D-206 决定。
6. **评估风险并决定去留：** 玩家综合当前状态、已有收获、前方目标和撤离成本，选择继续探索或尝试撤离。该节点是支柱2与支柱3的主要交汇点。
7. **撤离成功或角色死亡：** 本局进入结束状态。成功与失败的物品处理、死亡损失和保留规则必须遵照之后确认的 D-202，不在本提案中预设。
8. **结算与返回营地：** 展示本局结果，处理可保留的战利品，并让玩家进行下一局整备。局外经济、营地升级和长期成长由 D-206 决定；持久化方案 D-207 留到阶段2。

### 3.5 四大支柱在单局中的体现

状态：**体验目标提案。**

| 玩法支柱 | 单局中应提供的体验 | 避免出现的问题 |
|---|---|---|
| 魔法战斗爽感 | 有节奏的普通遭遇、具有辨识度的强敌，以及清晰的施法、命中和击败反馈 | 全程无差别刷怪，或战斗只成为拾取奖励的门槛 |
| 探索与搜刮价值 | 可读的环境线索、值得发现的兴趣点、路线选择和有差异的奖励机会 | 宝箱和资源平均散布，探索不产生判断或惊喜 |
| 撤离决策紧张感 | 收获越有价值，继续深入与安全结束之间的取舍越有意义 | 玩家没有理由提前撤离，或只因突然出现的强制倒计时而撤离 |
| 装备成长意义 | 本局发现的装备与资源能让玩家期待下一局的配置变化或长期成长 | 掉落只有数值高低，没有构筑意义；具体装备机制仍须 D-205、D-206 确认 |

### 3.6 节奏与体验检查标准

状态：**用于后续评估的设计检查项，不是数值验收门槛。**

- 前段是否给了玩家足够时间观察、移动、探索和理解威胁？
- 战斗是否有变化和间隔，而不是从进入地图起持续无休止地受袭？
- 玩家是否至少有机会作出有意义的探索/奖励选择？
- 深入高风险区域是否能让玩家理解「风险增加的原因」及潜在收益？
- 玩家是否会基于自己的收获和状态主动思考撤离，而不是只跟随系统倒计时？
- 战利品是否能连接到有意义的装备选择或跨局成长？具体连接方式待 D-205、D-206 决定。
- 如果玩家在 10 分钟左右结束本局，是否仍能获得完整、有收获感的体验？如果玩家继续到 15 分钟，是否能感受到额外风险与额外价值？

## 4. 操作与战斗设计

### 4.1 开发与验证优先顺序

状态：**已确认开发优先顺序；不改变双平台首发目标。**

- 项目首发平台仍为 PC 浏览器与手机浏览器，依据 D-004；手机优先不代表取消、缩减或降低 PC 版本的首发要求。
- **开发顺序：先完成手机端核心体验，再开发和适配 PC 端。**
- 阶段2仍须从技术架构层面考虑双平台：建立平台无关的游戏逻辑与输入接口，并进行必要的浏览器/设备技术验证；但不要求在阶段2完成 PC 端完整操作与 UI。
- 阶段3 M1 优先以手机浏览器为主要可玩验证目标，先跑通移动、战斗、探索、搜刮、撤离和结算的核心闭环。
- 后续阶段优先完善手机端完整体验，再接入 PC 键鼠输入与桌面 UI 布局；阶段6须完成双平台回归与验收。
- 不得采用「先写一套手机专用逻辑，之后复制一套 PC 逻辑」的方式。移动、战斗、技能、敌人、掉落和结算等规则应共享；平台差异集中在输入适配、UI 布局和显示交互层。

### 4.2 双端操作的共同原则

状态：**D-201 提案，待负责人确认具体操作方式。**

1. PC 与手机共享同一套战斗规则；不同平台只改变玩家输入方式、瞄准辅助和界面布局。
2. 普通攻击与技能都应由玩家主动触发，不建议采用完全自动、无需玩家输入的持续攻击。
3. 尽可能支持移动中攻击或施法；个别技能是否需要站定，按技能设计另行判断。
4. 触屏操作优先减少精细点击、长距离拖动和频繁切换操作模式。
5. 瞄准辅助只用于降低触控误差，不应无视玩家意图自动选择远处目标或自动释放技能。
6. 手机 UI 以双手拇指可触达区域为主要约束，同时注意屏幕边缘和浏览器系统手势区域。

### 4.3 手机触屏操作提案（优先设计）

状态：**提案/待确认（D-201）。**

推荐优先评估「左侧移动摇杆 + 右侧瞄准/攻击区 + 独立技能按钮」：

| 输入区域 | 建议功能 | 设计目的 |
|---|---|---|
| 左下区域 | 虚拟移动摇杆 | 控制移动方向与速度；固定摇杆或动态摇杆待可用性测试。 |
| 右下区域 | 瞄准与普通攻击 | 玩家拖动/指向确定攻击方向，并通过明确的触控动作触发普通攻击。 |
| 右侧技能区 | 主动技能按钮 | 让玩家无需离开移动摇杆即可触发技能；按钮数量与排列待技能数量确定后设计。 |
| 屏幕中央及周边 | 战场、敌人、掉落和危险提示 | 保持视野清晰，避免按钮遮挡关键战斗信息。 |

待讨论的手机瞄准方式：

- **方案 M1：双摇杆。** 左侧移动，右侧摇杆控制瞄准方向；右摇杆按下或单独按钮触发普攻。方向控制较直接，但需要玩家同时协调两个拇指。
- **方案 M2：移动自动朝向 + 攻击按钮。** 左侧控制移动，角色根据移动方向或附近威胁自动确定攻击方向，右侧按钮触发普攻。操作更简单，但玩家对攻击方向的控制较弱。
- **方案 M3：移动摇杆 + 点选/拖动瞄准 + 攻击按钮。** 保留方向控制，但触屏操作可能更复杂，需要验证小屏幕可用性。

当前建议：先以 **M1 双摇杆**作为原型比较基线，同时测试 M2 的操作效率；不能仅凭设计讨论定案，需在阶段3通过真实手机操作测试决定。M3 暂作为备选，不先增加实现复杂度。
